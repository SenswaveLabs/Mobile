# AGENTS.md

Senswave mobile is a DIY Smart Home app built with React Native, Expo and TypeScript.
Authentication, home selection, home/room/device creation and settings use local React Native Reusables components; the app renders native React Native UI.

## Rules

- Use the [caveman skill](.claude/skills/caveman/SKILL.md) for every chat response; code, commits and PR descriptions use normal prose.
- New UI work belongs on `next-dev`. Keep it separate from `main` until integration is explicitly requested.
- Never merge PRs autonomously. Notify on test failure and wait for human. Commit/PR titles start with `fix:`, `feat:` or `chore:`.
- Production releases are manual only, with strict versioning. Public CI verifies PRs with an ARM64 Android build and requests a release PR in private `Next-Infra`; a human merges that PR before the VPS builds and hosts the next-dev APK. Never give public `Mobile` a self-hosted runner or infrastructure write token. See [Tooling](docs/agent-guide/tooling.md).
- Build completion notifications call the local reusable `notify-discord.yaml` workflow with the repository `DISCORD_WEBHOOK_URL` Actions secret. See [Tooling](docs/agent-guide/tooling.md).
- Android CI checks compile ARM64 debug, export production JavaScript and upload Gradle profiles. Pushes and manual runs on `next-dev` seed Gradle cache for PRs. Validate release tasks and all supported ABIs before releases.
- Never call `fetch` outside `src/utils/httpClient.tsx`; use `useHttpClient()`.
- Home and Device icon choices come from backend catalogs. Keep opaque keys unchanged; see [Domain and API contracts](docs/agent-guide/api-and-data.md).
- Changes to shared API contracts require a backend build at `Senswave.sln` level.
- Use pnpm only, Node from `.nvmrc`, and the frozen pnpm lockfile. Keep the Node minimum in `package.json` and EAS profile versions aligned with `.nvmrc`. Keep every dependency version in `package.json` exact and preserve build approvals in `pnpm-workspace.yaml`.
- Run `pnpm hooks:install` once per clone to enable whole-repository formatting and lint before commits.
- Create `.env` from `.env.template` before the first run.
- Keep this index and the affected guide documents current in the same commit as changes to structure, stack, conventions, contracts, configuration or workflows.

## UI direction

All active next-dev screens, subforms, overlays and recovery states use the current native design system. Legacy render branches are retired; an existing wrapper/export never authorizes old UI. Every icon field uses the compact four-column BottomSheetSelect: Home/Device API catalogs, Dashboard16/Radio15 and the complete Automation318 palette. Preserve exact and historical keys and cancellation. Global RootToast/RootSiblingParent and automatic error-driven Keyboard.dismiss are retired on all routes, including unknown routes and delayed responses. Errors have a local Result/state/Alert/Retry owner; keep dashboard command snackbars and Home tile alerts. See [UI policy](docs/agent-guide/interface.md).

Material Design 3 guides UX and interaction; Senswave's shadcn-based product defines the visual language.
Shared dialog overlays own all safe-area insets and keep native actions vertical at every width. Option modals use one keyboard-aware scroll without a second keyboard-avoiding wrapper; see [UI policy](docs/agent-guide/interface.md).
Use `next-frontend/apps/web` as a brand reference; choose hierarchy and behavior for mobile tasks. Use React Native Reusables primitives for auth, home selection, creation and settings.
App components use `FC` and interface props; copied React Native Reusables primitives keep upstream signatures.
Editable details forms use `common/FormSection` for headings, field spacing and save actions.
Home's exit confirmation stays mounted during loading, no-home and read-error states; Android Back opens it and Cancel/Back dismisses it. Invitations require one routed home ID matching the current owned home. Capture the submitted home ID/name with the code, ignore stale visits and latch accepted POSTs before reading their code.
Live tile and command responses validate the matching device before changing local values or cache. Tile previews and widget forms validate consumed operation/configuration fields before mounting; preview failures have local Retry. Broker details validate matching IDs and all consumed settings fields; subscription failures retain only that broker's validated rows with GET-only Retry.
Broker details consume API `protocolVersion`/`useTls`, share one Save/Delete lock, and retire both tabs after accepted deletion; recovery returns only. Unknown list statuses stay unavailable with GET-only Retry. Failed initial Home reads offer Retry and Choose home. Create device requires the same ready managed home through submission and keeps accepted return recovery local. See the UI, API and validation guides.
Secondary list actions use `ContentSection.headerAction` and `SectionHeaderAction` beside the heading, following Devices/Add device. When a section has a helper and header action, place the helper below the full title/action row; keep it under the title when there is no action. Creation actions grow to the bottom of the same keyboard-aware scroll on tall screens; do not detach them from the form or place them immediately after short field groups.
On the home dashboard, only an assigned `Working` or `Connected` source gets a subtitle below the home name; Connecting/Restarting use neutral text and other states use persistent notices. Only known disconnected/Error or missing-source states can expose a separate source action, and only for owners. Settings and details retain their data-source state badges.
Native styling uses `StyleSheet.create()` and `useTheme()` colors; all screens share the themed background. React Native Reusables primitives use NativeWind and tokens derived from the same theme.
Data-source creation uses one keyboard-aware page with inline feedback; see the [mobile UI design policy](docs/agent-guide/interface.md) for its validation and navigation behavior.
Account data-source lists load the full catalog once per focus and keep Add and read recovery in the list header. List-row broker status errors use a local Retry that rereads status without activating the row. Home source selection requires the routed/current home to match and belong to the owner; accepted links refresh in the background and Retry never repeats the PUT. See the [mobile UI design policy](docs/agent-guide/interface.md) and [domain/API contracts](docs/agent-guide/api-and-data.md).
Broker client start uses one keyboard-aware `FormSection`, local credential restoration, inline feedback and accepted-once return navigation; see the [mobile UI design policy](docs/agent-guide/interface.md).
Broker subscription creation uses one keyboard-aware `FormSection`, topic validation, inline feedback and accepted-once return navigation; see the [mobile UI design policy](docs/agent-guide/interface.md).
Dashboard creation uses one keyboard-aware `FormSection`, preserved icon keys, strict string grid bounds, a bottom-aligned action on tall screens and accepted-once return; see the [mobile UI design policy](docs/agent-guide/interface.md).
Dashboard details use a keyboard-aware edit form, read-only grid details, partial saves, confirmed deletion and the compact icon bottom sheet from Create Home. Dashboard choices use their historical 16 icons; Radio options use their historical 15. Preserve existing keys outside those palettes without exposing global search in these flows; see the [mobile UI design policy](docs/agent-guide/interface.md).
Device reads validate consumed list/tile/configuration/readings/presence fields before replacing cache or mounting the editor; malformed entries preserve cached devices and local Retry. Device details use native Tile/Presence selectors and per-device operation fields with inline validation, preserve historical operation IDs through unrelated partial saves, and keep accepted-delete recovery local without repeating DELETE. Return only after the current-home device list refresh succeeds; failed reads keep local Retry, while later Retry/refocus may refresh or navigate only; see the [mobile UI design policy](docs/agent-guide/interface.md) and [validation guide](docs/agent-guide/validation.md).
Operation details mount only a validated matching read, keep the operation form read-only, and expose deletion only after proving current-home device membership and full per-device operation membership for an owner/manager. Keep delete and read recovery local: after accepted DELETE, Retry repeats only the matching device read until it succeeds, and then retries navigation without repeating DELETE. `/device/operation/list` remains a headerless compatibility route to `/device/widget/list`, forwarding a valid device ID; see the [mobile UI design policy](docs/agent-guide/interface.md) and [validation guide](docs/agent-guide/validation.md).
Device dashboards keep viewing and live widget controls available to all home roles; only owners/managers add, edit, place or unlink widgets. Bind reads, placement and unlink to the routed device/dashboard. Command errors use one dashboard-scoped snackbar with widget identity and guarded Retry; errors in an open color editor stay there. Errors must never resize grid rows or move other controls; see the [mobile UI design policy](docs/agent-guide/interface.md).
Dashboard grids remain visible when empty. Managers tap a free cell to choose a widget, then drag its preview to move and drag its corner to resize; placement uses no numeric fields or +/- controls. Existing placements require removal before re-adding because the API rejects duplicate widget IDs; see the [mobile UI design policy](docs/agent-guide/interface.md).
Dashboard identity, selection, management and the widget grid share one vertical scroll. Widget creation and read-only details use one keyboard-aware `FormSection`; type configuration uses native fields, inline validation and selection sheets. Widget definition deletion is a separate confirmed action from dashboard unlink; see the [mobile UI design policy](docs/agent-guide/interface.md).
Placement previews use a quiet neutral surface, thin outline and subdued resize affordance with a separate 48 dp hit area. Color selection uses a swatch/HEX field and a themed bottom-sheet editor; gestures and cancellation do not send commands. Operation creation includes its conditional and nested forms in the same native design system, with inline validation and accepted-once return; see the [mobile UI design policy](docs/agent-guide/interface.md).
Home location uses a native MapLibre picker with OpenStreetMap. See [Tooling](docs/agent-guide/tooling.md) for its development-client rebuild requirement.
Profile settings use one native scroll, immediate Light/Dark/System theme selection, read-only English, inline recovery, and a confirmed native account-deletion dialog; see the [mobile UI design policy](docs/agent-guide/interface.md).
Explicit Light/Dark overrides system appearance; only System follows it. Operation type markers use neutral theme foreground/surface pairs. Operation details show selectable configuration text, preserving values and the local deletion flow; genuine disabled controls retain their disabled styling.
The consent gate uses one native auth-style scroll with local account feedback. Only a verified active consent enters the app; acceptance is latched before silent account verification, and retry never repeats the POST. UserProvider validates consumed account fields before applying account/theme state and resolves transport, JSON and malformed-response failures through `Result`; theme persistence rejections are handled. Cancel, header Back and Android Back log out; legal-document Back returns to the gate. See the [mobile UI design policy](docs/agent-guide/interface.md) and [domain/API contracts](docs/agent-guide/api-and-data.md).
Email confirmation preserves opaque query values through native link entry and confirmation, rejects missing, empty or repeated route parameters, and offers local Retry and Sign in recovery. Retained retries recheck route identity and focus, then capture the current provider method before queueing; recreated context objects do not cancel same-link work. Legal pages share one growing scroll and accept only consumed server fields; public legal Back falls back to `/start`, while private Stack headers own their Back behavior. Maintenance recovery waits for initialization to settle before routing from current session state. App information keeps all metadata and legal links in one bounded scroll. See the [mobile UI design policy](docs/agent-guide/interface.md), [domain and API contracts](docs/agent-guide/api-and-data.md) and [validation guide](docs/agent-guide/validation.md).
Automations use a home-scoped list and token-bound parent/child forms. Child forms load the full operation catalog, keep exact typed values, and own field validation; routes own permission checks, awaited saved-child PUTs, draft-only local append and accepted-once return. Only owners add children to saved automations. Keep errors inline and suppress legacy toasts; see the [mobile UI policy](docs/agent-guide/interface.md) and [domain/API contracts](docs/agent-guide/api-and-data.md).
Automation rows expose Enabled/Disabled in their accessible names. Child operation selectors distinguish repeated names with type and a unique ID prefix, falling back to the full ID on prefix collisions; selected labels wrap and keep the same accessible identity. Drafts retain raw names and IDs. Required child selectors announce errors and scroll/accessibility-focus the first invalid field; shared expanders expose their button role and expanded state.
